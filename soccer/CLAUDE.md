# soccer — 감독 문서 1: 설계도

2000년 온라인 축구 게임(탑뷰 2D, 개성 스킬, 3:3~10:10, 반칙 없음)을 본뜬 **20인 온라인 축구**. PC 브라우저(키보드)와
모바일 브라우저(터치)에서 같은 `index.html`로 실행하고, 서버는 Node.js 하나다. 이 저장소의 다른 앱과 달리 **파일 여러 개 + 서버 + npm 의존성 1개(`ws`)** 를 가지며,
**이 문서의 규칙이 루트 `CLAUDE.md`보다 우선**한다. 루트 규칙 중 유지하는 것: 한국어 UI·주석, `:root` CSS 변수,
폰트 스택 `'Segoe UI', Pretendard, sans-serif`, 마우스/키보드 + 터치 양쪽 경로, `store` 래퍼, `file://`에서 연습장 모드 동작.

## 0. 감독 문서 체계 — 세션 시작 시 가장 먼저 읽을 것

| 문서 | 역할 | 누가 언제 고치나 |
|---|---|---|
| `CLAUDE.md` (이 문서) | 설계도. 파일 구성, 프로토콜, 구조 상수, 규칙 | 설계가 바뀔 때. 코드보다 **먼저** |
| `ROADMAP.md` | 9단계(+선택 1) 체크리스트. 완료 조건·확인 방법 | 단계 완료 시 체크. 조건 변경은 §0.2 |
| `HANDOFF.md` | 세션 인수인계 일지. 최신이 맨 위 | 세션이 끝날 때마다 |

세션 의식과 문서 수정 규칙은 `voxel-world/CLAUDE.md` §0.1·§0.2와 **동일**하다. 요점만 다시 적는다.

- 한 세션에 한 단계. HANDOFF 맨 위 항목 + ROADMAP "현재 단계"를 먼저 읽는다.
- 완료 조건은 **실측값**으로만 체크한다. 통과시키려고 조건을 낮추는 것은 사용자 확인 없이는 금지.
- 오류의 원인이 코드면 코드만, 설계면 이 문서를 먼저, 순서면 ROADMAP을 고치고 전부 HANDOFF에 기록한다.
- 게임플레이 튜닝 수치(속도·쿨다운·마찰 등)의 **정본은 `game-core.js`의 `TUNING`·`CHARACTERS` 객체**다. 이 문서엔 구조 상수만 둔다. 문서와 코드에 같은 숫자를 두 번 적지 않는다.

## 1. 범위

**목표**: 방(최대 20명, 팀당 1~10명) · 탑뷰 2D 경기(드리블 킥·패스·슛·감아차기·발차기, 자동 골키퍼) · 캐릭터 6종 × 필살기 1개 · RPG형 추적 카메라 · 전후반·득점·킥오프 ·
로비(방 목록·생성·팀·준비·채팅) · 경기 중 난입 허용 · **접속 시 지연 측정으로 느린 유저 거부** · 경기 중 지연 감시·퇴장 · 재접속 ·
부하 테스트로 20명 검증 · Lightsail 서울 배포 · PC 키보드 + **모바일 터치(같은 페이지)** · 윈도우 바탕화면 실행.

**모드는 둘이다**: **혼자 하기**(인공지능과 2:2, 서버 불필요 — `file://` 로도 된다)와 **여러 명이서 하기**(온라인, 서버 필요).
시작 화면에서 고른다. 온라인은 아이디(닉네임)만 입력하며 **회원가입·비밀번호 계정이 없다**(보안 책임을 지지 않으려는 결정, §1 범위 밖과 같은 이유).

**연습장 인공지능** (2026-08-25 사용자 지시로 범위에 들어옴): **혼자 할 때는 인공지능과 2:2** 로 경기한다.
`SoccerCore.AI.think(state, slot)` 이 입력을 만들어 주는 방식이라 `step()` 안에는 들어가지 않는다 — 서버 권위와 결정성은 그대로다.
**온라인은 여전히 봇이 없다**(사람이 나가면 빈자리). 즉 인공지능은 오프라인 연습장 전용이다.

**범위 밖** (이유): 온라인 방의 필드 플레이어 봇(사용자 결정: 사람이 없으면 빈자리로 둔다 — 골키퍼만 예외로 자동) · 안드로이드 APK(모바일은 브라우저로, 필요하면 추후) ·
계정·비밀번호(보안 책임 회피, 닉네임만) · 오프사이드·반칙·스로인(벽으로 대체) · 길드·랭킹 · 관전.

**법적 경계**: 원작 이름·캐릭터·스킬명·그림체·효과음을 쓰지 않는다. 메커닉(탑뷰·스킬·인원·반칙 없음)만 가져온다.
표시 이름 **"반대항축구"** (2026-08-24 사용자 확정, 띄어쓰기 없이). 학교 반대항 경기의 "반 전원 출전" 기억을 20인 난전과 연결한 이름이다.
이 이름이 세계관을 정한다: **팀 = ○반**, 캐릭터 = 반 친구 유형, 휘슬 = 체육 선생님. 캐릭터·필살기 이름은 §5.3 표가 정본이다.

## 2. 기술 결정 — 바꾸려면 이 문서를 먼저 고친다

- **클라이언트** = `index.html` + 공유 `game-core.js` + 그림 전용 `sprites.js`. 캔버스 2D, 키보드 + 터치(가상 조이스틱·버튼, 같은 `keys` 맵에 키 코드를 넣는 방식) 입력, 브라우저(크롬/엣지/모바일 크롬·사파리) 실행. 번들러·CDN 없음.
- **선수는 등속**(2026-08-24 사용자 지시): 가속·감속이 없다. 입력 즉시 최고 속도, 떼면 즉시 정지.
- **공은 굴러가며 느려진다**(2026-08-25 7차 지시로 공의 등속은 버렸다): 실제 이동 속도가 **남은 거리의 제곱근**에 비례한다 = 실제 공처럼 **일정한 감속도**.
  선형(`slowMin + (1−slowMin)·frac`)으로 하면 끝에서 속도가 `slowMin` 인 채로 뚝 끊겨 "갑자기 멈추는" 느낌이 났다(9차 지시로 교체).
  `slowMin`(0.06)은 마지막 한 틱이 무한히 늘어지지 않게 두는 바닥값일 뿐이다.
  **`range` 는 여전히 "총 이동 거리"라서 날아가는 거리는 그대로이고 속도 곡선만 바뀐다** — 그래서 이 변경으로 기존 거리 실측값이 하나도 흔들리지 않았다.
  실측: 최대 슛이 20틱 동안 틱당 **30.8 → 29.5 → 28.3 → … → 8.3 → 6.6 → 3** 으로 매끄럽게 줄며 총 368 을 간다.
- **서버** = Node.js LTS(22 이상) + `ws`(유일한 npm 의존성). 정적 파일(`index.html`, `game-core.js`)도 같은 프로세스의 `http` 모듈이 서빙한다. 포트 하나.
- **시뮬레이션은 한 번만 쓴다.** `game-core.js`는 UMD 래퍼로 브라우저에선 `window.SoccerCore`, Node에선 `module.exports`. 서버가 돌리는 `step()`과 연습장 모드가 돌리는 `step()`이 **같은 함수**다. 이 덕분에 나중에 "내 캐릭터 예측"(선택 10단계)을 넣을 수 있다.
- **서버 권위**: 클라이언트는 입력만 보낸다. 위치·득점·쿨다운은 전부 서버가 정한다. 클라이언트는 스냅샷을 보간해서 그릴 뿐이다(1차는 예측 없음).
- **전역은 `SoccerCore` 하나**(`game-core.js`가 만든다). `index.html`의 IIFE는 `SoccerCore.debug`만 덧붙인다.
- **`fetch` 금지**는 연습장 모드(`file://`)에 한한다. 온라인 모드는 WebSocket만 쓴다. 서버 URL은 페이지 origin에서 유도(`ws://` ↔ `wss://`는 `location.protocol`로 결정).
- **스냅샷·입력은 바이너리**(`DataView`), 나머지 메시지는 JSON 텍스트. 인코딩/디코딩 함수는 `game-core.js`에 두고 양쪽이 공유한다.
- **봇 없음.** 빈 슬롯은 비어 있다. 경기 중 나가면 슬롯이 비고 경기는 계속된다.
- **호스팅**: AWS Lightsail 서울(ap-northeast-2), Linux, $7/월(1GB·2vCPU·40GB·전송 2TB, 첫 3개월 무료), 고정 IP. 0단계 테스트는 개발 PC + Cloudflare 퀵 터널.
- **저장**: 클라이언트는 `store`로 `soc_nick`, `soc_settings`만. 서버는 디스크 저장 없음(프로세스 재시작 = 방 초기화).

## 3. 구조 상수

| 상수 | 값 | 비고 |
|---|---|---|
| `PROTOCOL_VERSION` | 정수, `game-core.js` 상단 | 클라이언트 `hello.v`와 다르면 4002로 거부 |
| `TICK_HZ` | 20 | 서버 틱 = 50ms. 연습장 모드도 동일 |
| `SNAPSHOT_EVERY` | 1 | 틱마다 스냅샷. 2단계 서버에서 도입 예정(지금은 코드에 없다) |
| `INTERP_MS` | 기본 100, 설정 50~150 | 클라이언트 렌더 시각 = 서버 시각 − INTERP_MS. 연습장은 로컬이라 50 고정 |
| `INPUT_HZ` | 20 | 틱마다 입력 1개. 서버는 초당 30개 초과 시 버림 — 2단계에서 도입 |
| 경기장 | 1200 × 800 단위, 원점 좌상단 | **전체가 보이지 않는다.** 카메라가 플레이어를 따라간다(§7 시야) |
| 시야 | 보이는 **넓이** 고정: PC 230,400(16:9에서 640×360) · 터치 195,000(812×375에서 650×300). 가로 300~880 · 세로 최소 288 | 화면이 커도 더 보이지 않는다 — 온라인 공평성. 클라이언트 전용 |
| 골대 | 폭 200(y 300~500), 깊이 40 | 공 중심이 골라인을 골대 안에서 넘으면 득점. **입구 판정은 골라인을 넘는 순간의 y**(이동 후 y로 보면 강슛이 기둥 밖을 지나고도 골이 된다). **들고 있는 공도 골대 입구 폭 안에서는 골라인을 넘는다** — 몰고 들어가는 득점이 된다(2026-08-25 사용자 지시). 입구 밖에서는 여전히 경기장 안으로 잡아 둔다 |
| 경계 | 벽(반발) | 아웃·스로인·코너 없음 |
| 반지름 | **선수 18**, 공 6 | 2026-08-25 4차 지시로 14 → 18(서로 때리기 쉽게). 골키퍼도 18, 소유 반지름 28, 앞차기 48 로 같이 올렸다. 걷기 속도는 220 → 185 → 160 → **168** 로 조정했다. **선수끼리·골키퍼와 닿아도 서로 밀지 않는다**(2026-08-25 3차 지시) — 겹쳐 지나갈 수 있고,
밀려나는 것은 발차기·방귀에 맞았을 때의 넉백뿐이다 |
| 골키퍼 | 진영마다 1명 자동 | x 는 골라인에서 24 고정. y 는 **`state.tick` 만의 사인 함수**(주기 3초·진폭 86, 좌우 위상 π 차이) — 공·선수와 무관하다. 닿은 공은 잡지 않고 튕겨낸다. 찬 공(`saveR`)보다 **몰고 오는 공(`stealR`)을 더 넓게** 걷어낸다 |
| 인원 | 방 최대 20, 팀당 `teamSize` 1~10 | 슬롯 id 0~19, 팀 0 = 왼쪽 시작 |
| 전반 길이 `halfSec` | 90 / **180**(기본) / 300 | 방 생성 시 선택. 하프타임 5초, 킥오프 정지 2초, 종료 화면 10초.
**시계는 `play` 중에만 줄어든다** — 세리머니·킥오프 정지는 경기 시간에서 빠진다(2026-08-25 사용자 지시) |
| 경기 단계 `phase` | `lobby → kickoff(2초) → play → half(5초) → kickoff(2초) → play → end(10초) → lobby` | 후반에 진영 교대 |
| 득점 직후 | `play → goal(1.2초, 공은 골망 안에서 계속 구름) → kickoff(0.8초, 위치 초기화) → play` | 합계 2초 정지 |
| 지연 게이트 | 핑 8개 × 100ms 간격, 중앙값 ≤ 100ms, 상위 10% ≤ 160ms, 응답 제한 1000ms | `server/config.json` `gate` |
| 경기 중 감시 | 2초마다 핑, 최근 10개 중앙값 > 150ms 또는 3회 연속 무응답 → 퇴장 | `config.json` `inMatch` |
| 재접속 | 끊긴 슬롯 15초 보존, 토큰으로 복귀 | |
| 제한 | IP당 접속 3, 방 20개, 닉네임 2~12자, 채팅 200자·초당 5개, 텍스트 프레임 2KB, 바이너리 8B | 초과 시 4005 |
| 종료 코드 | 4001 NET_SLOW · 4002 VERSION · 4003 ROOM_FULL · 4004 KICKED · 4005 RATE_LIMIT · 4006 DUP_IP | 클라이언트는 코드별 한국어 문구 |

## 4. 파일 구성

```
soccer/
  CLAUDE.md  ROADMAP.md  HANDOFF.md
  index.html          클라이언트: CSS(:root 변수), 캔버스 렌더, 입력, 로비 UI, 보간, WebSocket, 연습장 모드, SoccerCore.debug
  game-core.js        공유: TUNING, CHARACTERS, createState, step, 득점·단계 전이, encode/decodeSnapshot, encode/decodeInput, hashState
  sprites.js          클라이언트 전용: 도트 캐릭터 그리기(window.SoccerSprite). 없으면 index.html 이 원으로 폴백
  server/
    server.js         http 정적 서빙 + ws. 접속 게이트, 방·슬롯, 틱 루프, 입력 수집, 스냅샷 브로드캐스트, 감시, /stats
    config.json       port, gate, inMatch, limits
    package.json      dependencies: { ws }. scripts: start, loadtest
    loadtest.js       가짜 클라이언트 N명 × 방 M개. --delay 로 인위 지연(게이트 검증)
    soccer.service    systemd 유닛 (Restart=always)
    deploy.ps1        scp + ssh 재시작. 키 경로는 deploy.local.json(커밋 금지)
    make-shortcut.ps1 바탕화면 바로가기: msedge --app=http://<서버>/ (8단계)
    .gitignore        node_modules/, deploy.local.json
  tools/
    headless-probe.js 검증 도구. 헤드리스 크롬을 DevTools 프로토콜로 붙여 실제 fps·스냅샷 Hz·키보드 경로를 재고 HUD 포함 PNG 를 저장
```

규칙:
- `game-core.js`는 **DOM·WebSocket·Node API를 참조하지 않는다.** 순수 계산만. 시간도 인자로 받는다(`Date.now()` 금지 — 결정성).
- `step(state, inputsBySlot)`은 `state`를 제자리에서 갱신하고 이벤트 배열을 반환한다(`play`·`goal`·`kickoff`·`half`·`end`·`lobby`·`kick`·`backkick`·`hit`·`shoot`·`curve`·`pass`·`dribble`·`ult`·`keeperSave`). 같은 입력 → 같은 `hashState`.
  반환 배열은 **매 틱 재사용**되므로 보관하려면 복사해야 한다.
- 핫루프(틱·인코딩·렌더)에서 객체 생성 금지. 스냅샷 `Uint8Array` 는 호출자가 재사용 버퍼를 넘긴다(`encodeSnapshot(state, ms, buf)`).
  `DataView` 는 매 호출 새로 만든다 — 버퍼 길이가 인원수에 따라 바뀌기 때문이다(20명 기준 1틱 1개, 측정상 무시 가능).
- 서버는 클라이언트를 믿지 않는다: 모든 수신값을 범위 검사하고 어긋나면 버린다(끊지 않음). 프레임 크기 초과·속도 초과만 4005로 끊는다.
- `console.error` 0 기준. 서버 로그는 `console.log` JSON 한 줄(`{t, ev, ...}`).

## 5. 게임 규칙과 캐릭터

### 5.1 조작 (2026-08-24 사용자 지시로 전면 개편)

| 동작 | 키 | 터치 버튼 | 비고 |
|---|---|---|---|
| 이동 | 방향키 | 왼쪽 아래 가상 조이스틱 | 등속. 방향만 쓴다 |

WASD 이동은 W·S·A·D 가 전부 동작 키라서 쓰지 않는다. **기존 C 태클은 없어졌다** — 발차기(D)가 그 역할을 한다.

버튼은 `keys` 맵에 키 코드를 넣으므로 입력 경로가 키보드와 완전히 같다.

### 5.2 규칙

- **이동**: 등속. 입력 방향 × `maxSpeed`(캐릭터 배율), 떼면 즉시 0. 대각선도 같은 속도.
- **달리기(왼쪽 Shift)** (2026-08-25 사용자 지시): 누르고 **실제로 움직이는 동안만** 체력이 준다.
  체력이 있으면 `sprintMul` 배(공을 몰고 있으면 `sprintCarryMul` 배 — 몰고 들어가 넣는 것이 너무 쉬워지지 않게 덜 빠르다),
  **0이 되면 걷기보다도 느려진다**(`tiredMul`, 2026-08-25 2차 지시). 다시 달리려면 `staminaResume` 까지 회복해야 하고, 그때까지 계속 느리다.
  달리지 않는 동안(정지·기절·정지 프레임 포함) 회복한다. 킥오프·득점 리셋 때 만충.
  달리기와 필살기 속도 효과(질주·돌진)는 **곱하지 않고 더 큰 쪽만** 쓴다 — 겹치면 좁은 시야에서 화면 밖으로 튀어나간다.
- **공 소유(드리블)**: 공이 선수 반지름 + 10 안에 들어오면 그 선수의 `owner`가 되고 진행 방향 앞 18단위에 붙어 같이 움직인다.
- **드리블 킥(W)**: 누른 시간(0~0.6초)만큼 멀리 찬다. **뗄 때** 나간다.
  거리는 충전의 `rangePow`(1.35) 제곱에 비례한다 — 지수가 2면 짧게 누를 때 너무 안 나가고, 1이면 톡 쳐도 멀리 간다.
  실측(6차): 누른 틱 1/3/6/9/12 에 공이 선수 앞 **58 / 98 / 178 / 274 / 382**.
  공만 빠르고 선수는 그대로라 길게 찰수록 **공을 잃을 위험**이 커진다 — 수비를 벗기되 거리를 스스로 정하는 셈이다.
- **공의 이동**: 찬 순간의 속도로 등속, `range`가 0이 되면 멈춘다. 벽에 맞으면 속도는 그대로 방향만 반사되고 남은 거리가 60%(골망 안 30%)로 준다.
- **슛(D)**: **충전이 없다**. 누르는 순간 **항상 같은 속도(640) · 같은 거리(400 = 경기장 가로의 정확히 1/3)** 로 나간다. 자동 조준 없음.
  거리는 2200 → 1200 → 700 → 500 → **400** 으로 계속 줄여 왔다. 세기를 바꾸는 것은 캐릭터 `shot` 배율과 에이스형 대포알뿐이다.
  **감아차기 거리는 슛과 같다**(10차 지시). 즉 `curve.range` 는 항상 `shoot.range` 와 같은 값을 유지해야 한다 — 한쪽을 바꾸면 다른 쪽도 바꾼다.
  **충전하는 기술은 이제 감아차기(Q/E)와 드리블(W) 둘뿐이다.**
- **감아차기(Q/E)**: 속도 480(캐릭터 shot 배율)·거리 1400 으로 나가되 **매 틱 방향이 회전**한다(`ball.spin`). 충전 0~0.6초 → 회전율 0.008~0.048 rad/틱,
  총 회전은 `turnMax` 에서 끊는다(없으면 공이 되돌아온다). Q = 화면 왼쪽(반시계), E = 오른쪽. 벽에 맞으면 회전이 절반으로 죽는다.
  2차 지시로 더 휘게 했다가 5차 지시로 조금 되돌렸다(`spinMax` 0.072 → 0.052, `turnMax` 2.7 → 2.0rad).
- **발차기(D, 공 없을 때)**: 앞 부채꼴(반지름 **56**·**±60°**, 캐릭터 `kickRange` 배율) 안의 상대를 **기절 2초 + 넉백**시킨다.
  44·±55° → 68·±70°(6차, 너무 좁아서) → **56·±60°**(7차, 너무 넓어서). 실측 격자 861칸 중 224칸 명중(26%), 최대 거리 56 · 최대 각 60°.
  판정은 **누른 그 틱에 바로** 일어난다. 꾹 누르고 있으면 쿨다운마다 반복된다(연타와 성능이 같다).
- **공을 차는 동작은 사람을 때리지 않는다**(6차 지시). 내부적으로 `kickKind` 를 셋으로 나눈다 —
  **1 앞차기(사람을 때림) · 2 방귀(사람을 때림) · 3 슛·감아차기(공만 참)**. `kickHits` 는 3 을 건너뛴다.
  전에는 슛을 쐈는데 앞에 서 있던 상대가 발차기에 맞아 기절했다.
- **동작 중에는 완전히 멈춘다**(6차 → 8차로 강화). 발차기·방귀·슛 동작(`kickT > 0`) 동안 **이동도 회전도 없다.**
  `frozen = freezeT > 0 || kickT > 0` 이라 그동안은 입력 자체를 받지 않는다(새 기술도 못 쓴다 — 쿨다운이 동작보다 길어 실전 손해는 없다).
  실측: 방귀 직후 대각선으로 계속 밀어도 5틱 동안 이동 0 · 각 0 을 유지하다가 동작이 끝난 틱부터 움직인다.
- **기절 중에도 밀리지 않는다**(8차 지시). 넉백(`knockback`·`knockTicks`)을 0 으로 껐다 — 맞은 선수는 제자리에서 굳는다.
  실측: 발차기에 맞은 뒤 12틱 동안 이동량 0. (공은 여전히 튕겨 나간다 — 사람만 안 밀린다.)
  코드 경로와 해시 항목은 남겨 두었으니 되살리려면 두 값만 올리면 된다.
- **방귀(S)** — 2026-08-25 3차 지시로 뒷발차기를 대체했다. 능력치는 뒷발차기 그대로이고 **판정 모양과 크기만 다르다**:
  · **공을 차지 않는다.** 공을 가진 채로 써도 공은 그대로 내 발 앞에 있다.
  · 판정이 **바라보는 방향의 뒤쪽 정사각형**이다(4차 지시로 "선수 중심 사방" → "뒤쪽만"). 앞모서리가 선수 중심을 지나고
    뒤로 한 변(2×`fartHalf`)만큼 뻗으며 옆으로 ±`fartHalf`. 캐릭터 `kickRange` 배율이 곱해진다.
    크기는 70 → 48 → **44.26** 으로 줄여 왔다(8차 지시 "면적 15% 축소" = 한 변에 √0.85). 실측 한 변 88.5.
    **클라이언트가 판정과 완전히 같은 식으로 같은 사각형을 그린다**(`index.html` 의 translate+rotate+fillRect) — 그림과 판정이 어긋나면 안 된다.
    실측(6단위 격자): 앞뒤 [−138, 0] · 좌우 [−66, +66], 앞쪽 50 은 안 맞고 뒤쪽 150·옆 75 도 안 맞는다.
  · **맞은 상대가 공을 갖고 있었으면 그 공이 나에게 넘어온다**(`steal` 이벤트). 상대가 기절 면역이거나 돌진 중이라 안 넘어가면 빼앗기도 실패한다.
  즉 "붙는 수비를 사방으로 떼어내면서 공까지 뺏는 기술"이다. 대신 정지 시간이 길어 헛방귀는 역공을 부른다.
- **차는 사람도 멈춘다** — 이 정지가 "쏘는 순간 역공당하는" 타이밍 싸움을 만든다.
  4차 지시로 한 틱씩 줄여 **발차기 0.05초(1틱) · 슛 0.10초(2틱) · 방귀 0.10초(2틱)** 이다. 쿨다운은 앞차기 0.6초 / **방귀 0.4초**(10차 지시로 0.8 → 0.4).
  방귀는 **누를 때마다 한 번**(연타 판정)이라 꾹 누르고 있어도 반복되지 않는다 — 실측 최소 간격 8틱 = 0.4초.
- ⚠ **기절 면역을 폐지했다**(4차 지시 "타격범위에 상대방이 있으면 무조건 기절"). 판정 안에 들어오면 방금 깨어난 상대도 즉시 다시 기절한다.
  유일한 예외는 덩치형 필살기 「황소 돌진」이다(그 필살기의 존재 이유가 무적이라 남겼다).
  **대가**: 기절 2초 > 발차기 쿨다운 0.6초 이므로 한 명이 상대를 계속 눕혀 둘 수 있다 — 최악 조건 실측 자유 시간 **200틱 중 32틱(16%)**.
  (면역이 있던 3차까지는 56% 였다.) 되돌리려면 `TUNING.player.stunImmuneTicks` 를 올리면 되고, **사용자 확인 없이 되살리지 말 것.**
  **영구 기절 잠금을 막는 것은 이제 「깨어난 뒤 2.5초 기절 면역」(`stunImmuneTicks`) 하나뿐이다.** 기절 2초 > 쿨다운 0.6초 라서
  예전의 "기절 < 쿨다운" 부등식은 성립하지 않는다. 면역 시간을 줄이면 한 명이 상대를 반영구적으로 눕힐 수 있으니 **줄이지 말 것**
  (실측: 최악 조건 200틱 중 자유 112틱 = 56%).
- **골키퍼(자동)**: 진영마다 하나, 골라인 앞 x=24 고정. y 는 `state.tick` 만의 사인 함수(주기 3초, 진폭 86 → y 314~486, 좌우 위상 π 차이)라
  **공·선수와 전혀 무관하게 주기적으로 왕복**한다(사용자 지시). 닿은 공은 **잡지 않고 튕겨낸다**(속도 560·거리 760, 골라인 반대쪽으로 강제).
  막는 반지름은 30(팔을 뻗은 판정, 판정 폭 76 = 골대 폭의 38%), 몸통 반지름은 14. 빠른 공이 뚫지 않도록 이동 선분으로 스윕 판정한다.
  **몰고 오는 공(소유 중인 공)도 걷어낸다**(2026-08-25) — 몰고 들어가는 득점의 유일한 방어 수단이라 판정 반지름이 찬 공(`saveR`)보다 넓다(`stealR`).
  단 **공격당하는 쪽 골키퍼만** 뺏는다
  (자기 진영 골키퍼까지 뺏으면 수비가 공을 몰고 나올 수 없다). 뺏긴 선수는 `touchCdTicks` 동안 다시 잡지 못한다.
  실측 방어율: 근거리 강슛 37% · 원거리 강슛 44% · 약한 슛 50% · **몰고 들어오기 56%**(골문 앞 200에서 출발 — `stealR` 을 올린 뒤).
- **득점 후**: 실점 팀 킥오프, 2초 정지. **하프타임**: 진영 교대. 동점 허용(연장 없음).
- **난입**: `play` 중에도 인원이 적은 팀으로 들어갈 수 있다. 자기 진영 기본 위치에 등장.
- **팀 이름**: 방 생성 시 두 팀의 반 번호(1~12반)를 고른다. 기본 1반 vs 2반. 득점판·채팅·종료 화면 모두 "3반 2 : 1 7반" 형식.

### 5.3 캐릭터 6종과 필살기(A)

게이지는 시간이 지나면 찬다(45초 만충). 득점하면 **실점한 팀에 더 많이** 준다(+8초 vs +2초) — 이긴 팀이 더 강해지는 눈덩이를 막는다.
발차기에 맞아도 +3초. 수치의 정본은 `CHARACTERS`이고, 판정은 전부 서버의 `step` 안에서만 일어난다(난수 없음).

**걷는 속도는 6종이 모두 같다**(1.00, 2026-08-25 7차 지시). 속도 차이는 필살기(전력 질주·황소 돌진)에서만 난다.

| 캐릭터 | 속도 | 슛 | 발차기 | 필살기 | 효과 |
|---|---|---|---|---|---|
| 체육부장형 | 1.00 | 1.00 | 1.00 | 집합 호루라기 | 반경 200 안 상대 전원 1.2초 기절 (즉발) |
| 에이스형 | 1.00 | 1.25 | 0.90 | 대포알 | **다음 슛 한 발**이 1.55배 + 골키퍼 관통 (5초 안에 쏴야 함). 자기 진영 골키퍼는 못 뚫는다 |
| 전학생형 | 1.00 | 1.00 | 1.00 | 슬쩍 이동 | 바라보는 쪽으로 240 순간이동(공도 함께) |
| 덩치형 | 1.00 | 1.10 | 1.40 | 황소 돌진 | 3초간 기절 면역 + 1.45배 속도, 닿은 상대 기절 |

「발차기」 열은 `CHARACTERS[].kickRange` — 발차기 판정 반지름에 곱해진다(덩치형은 44 → 61.6).
필살기의 기절 시간(광역 1.2초·돌진 0.8초)은 **일반 발차기 기절 2초보다 짧다** — 필살기의 값은 "여러 명을 한꺼번에"나 "무적 이동"이지
기절 길이가 아니다. 바꾸려면 사용자 확인을 받는다.
득점·하프타임 리셋 때 **발동 중이던 필살기 효과는 지워진다**(게이지는 유지). 기절 면역은 `stunPlayer` 한 곳에서만 판정한다.

### 5.4 캐릭터 스프라이트 (`sprites.js`)

캐릭터 그림은 `sprites.js`가 그린다. **클라이언트 전용**이라 서버·시뮬레이션과 무관하고, 파일이 없거나 깨지면
`index.html`의 `fallbackDraw`(원 + 방향 삼각형)로 자동 폴백한다. 화풍은 **납작한 종이 도트**(**30×26** 격자를 오프스크린 캔버스에 굽고 정수배 확대. 2026-08-25 에 24 → 30 으로 넓혔다 — 발차기 발끝이 잘렸다).
2026-08-25 3차 지시로 입체 도트에서 **종이 오려 붙인 느낌**으로 바꿨다 — 이유는 그림이 아니라 **판정**이다:
서 있는 사람을 3/4 시점으로 그리면 그림이 발밑 충돌 원(반지름 14)보다 훨씬 커서 "어디까지가 맞는 범위인지" 헷갈렸다. 그래서
① 테두리를 밝은 종이색(`OUTLINE`)으로 ② 명암을 `FLAT_SHADE`(0.22)까지 줄여 평평하게 ③ 화면에 그릴 때 세로로 `FLATTEN`(0.62) 누르고
**가로로 `WIDEN`(1.45) 늘려** 실루엣을 정사각형에 가깝게 만들고(4차 지시) ④ **발밑에 충돌 반지름 그대로의 원반과 흰 테두리**를 그린다.
그 원이 곧 판정이다. 도안(`BODY`)은 손대지 않고 **그릴 때만** 늘이고 누르므로 픽셀 도안은 그대로다.
선수 반지름이 18 로 커지면서 그림도 함께 커져, 이제 그림 폭이 충돌 지름(36)과 거의 같다. `namsan-rpg`의 도안 방식과 같은 계열이다.

계약: `window.SoccerSprite = { STYLE, CHARACTERS, draw(ctx, o) }`.
`o = { x, y(발 밑 중앙), r(화면상 충돌 반지름), charId(0~5, 6=골키퍼), team, facing(라디안, 0=오른쪽),
motion('idle'|'run'|'kick'|'backkick'|'stun'|'ult'), t(초), phase(0~1), hasBall, ultActive, charge(0~1) }`.
**순수 함수여야 한다** — 내부에 난수·현재시각·가변 전역 금지(같은 `o` → 같은 그림).
캐시 키는 `charId|team|view|pose|frame`(크기는 정수 배율이라 키에 없다) — 결정적이면 어떤 키 조합이든 무방하다.

캐릭터 6종은 능력에 맞춰 **체형·머리·소품이 서로 다르다**(`BODY` 표): 체육부장 = 벌어진 어깨 + 호루라기, 에이스 = 긴 머리 + 완장 + 흰 축구화,
전학생 = 마른 장신 + 안경, 덩치 = 어깨 두 배 + 큰 발, 육상부 = 긴 다리 + 러닝셔츠 + 헤드밴드, 장난꾸러기 = 작고 통통 + 삐친 머리.
여기에 2026-08-25 에 두 가지를 더했다 — **캐릭터 고유색 허리띠**(`BODY[].acc`, 팀색이 같아도 어느 방향에서든 누가 누군지 구분된다)와
**걸음 위상차**(`frameOf` 에 `charId * 0.137` 을 더한다 — 여럿이 한 화면에 있어도 똑같이 뛰지 않는다).

#### 5.4.1 도트 대신 **이미지 파일**을 쓸 때의 규격 (2026-08-25 사용자 요청, 파일 대기 중)

사용자가 캐릭터 그림 파일을 주면 도트 도안 대신 붙일 수 있다. 그때 지켜야 할 계약:

| 항목 | 값 |
|---|---|
| 위치·이름 | `soccer/chars/<key>.png` — key 는 `BODY[].key` 그대로: `captain` `ace` `transfer` `big` `runner` `prank` `keeper` |
| 형식 | **PNG(투명 배경, 알파 채널)**. SVG·WebP 도 가능하지만 PNG 가 가장 안전하다 |
| 시점·방향 | **위에서 내려다본 그림, 오른쪽(3시 방향)을 보는 자세 한 장.** 코드가 8방향으로 회전시킨다 |
| 크기 | 정사각형 **256×256** 권장(최소 128). 화면에서는 반지름 18단위(보통 34px)로 그려진다 |
| 여백 | 몸이 이미지 정중앙, **이미지 한 변이 곧 충돌 지름(36단위)** 이 되도록 꽉 채운다. 그래야 그림과 판정이 일치한다 |
| 팀 구분 | 한 장만 주면 팀은 발밑 원반 색으로만 구분된다. 유니폼까지 나누려면 `captain-a.png` / `captain-b.png` 처럼 두 장씩 |
| 동작 | 정지 그림 한 장이면 충분하다. 원하면 `<key>-kick.png` · `<key>-fart.png` 를 더 줄 수 있다 |
| 용량 | 한 장 200KB 이하, 전체 2MB 이하 |

**법적 경계**(§1): 다른 게임에서 가져온 그림은 쓸 수 없다. 직접 그렸거나 라이선스가 확인된 것이어야 한다.
파일이 없으면 지금처럼 `sprites.js` 의 도트 도안으로 그린다(폴백은 그대로 유지한다).

### 5.5 소리 (`index.html`)

**음원 파일이 없다.** 이 저장소는 CDN·외부 에셋을 쓰지 않으므로 효과음과 배경음악을 전부 WebAudio 로 합성한다(2026-08-25 사용자 지시).

- **AudioContext 는 첫 조작(키·터치·클릭) 뒤에만 만든다.** 그 전에는 모든 호출이 조용히 무시된다 — 자동재생 정책 경고를 콘솔에 남기지 않기 위해서다.
- 효과음은 `step()` 이 낸 이벤트에 붙는다: `kick` `fart` `shoot` `curve` `pass` `dribble` `hit` `steal` `keeperSave` `ult` `goal` 과 휘슬(`kickoff`/`half`/`end`).
  **위치가 있는 소리는 그 선수가 화면 안일 때만** 낸다(20명이 되면 화면 밖 소리까지 다 울려 시끄럽다).
- 배경음악은 132BPM 4마디(Am–F–C–G) 순환. 8분음표 격자에 베이스·아르페지오·하이햇을 **0.25초 앞서 예약**한다(`setInterval` 60ms 룩어헤드).
  잡음원은 고정 시드로 만들어 매번 같은 소리가 난다.
  마디마다 **한 마디를 덮는 패드 두 음**을 함께 깐다. 패드는 `env()` 의 지수 감쇠가 아니라 전용 `pad()`(올라가서 유지하다 내려오는 포락선)를 쓴다 —
  지수 감쇠는 0.5초면 사실상 사라져서 음 사이가 완전히 비었다.
- **음악이 음악처럼 들리게**: 화음만 굴리면 "배경 웅웅"으로 들려서 마디마다 **4분음표 멜로디 한 줄**(`MEL`)을 얹었다. 구성은 베이스 + 패드 2음 + 아르페지오 + 멜로디 + 하이햇.
- **♪ 단추가 출력 세기에 맞춰 빛난다**(10차). 사용자가 "소리가 안 들린다"고 할 때 원인이 페이지 안인지 밖인지 가르는 장치다 —
  **단추가 빛나는데 안 들리면 원인은 페이지 밖**(브라우저 탭 음소거 · 윈도우 볼륨 믹서 · 출력 장치)이다.
- **소리가 실제로 나오는지 재는 법**: `master` 에 분석 노드를 달아 두었다. `debug.audio().level` 이 마스터 출력의 RMS(0~1)다.
  실측(2026-08-25, 헤드리스 크롬 + 진짜 키 입력): 처음 **최대 0.027 · 평균 0.004 · 표본 다수가 0**(사실상 무음) →
  음량·패드 보강 후 **최대 0.101 · 평균 0.047** → 멜로디 추가와 `bgmG` 0.75 로 **최대 0.130 · 최소 0.026 · 평균 0.060**.
  같은 잣대로 잰 효과음 최고치는 발차기 0.114 · 슛 0.200 · 골 0.148 이라 **BGM 은 효과음과 비슷한 크기**다.
  `debug.audio()` 는 `{ready, state, sfx, bgm, bgmRunning, level}` 을 준다.
- 탭이 숨겨지면 `AudioContext` 를 `suspend`, 돌아오면 `resume`. 끄고 켜기는 N(효과음)·B(배경음악) 또는 왼쪽 위 단추, 설정은 `soc_settings`.

### 5.6 연습장 인공지능 (`SoccerCore.AI`)

혼자 할 때 2:2 를 만드는 최소한의 인공지능이다. **규칙**:

- **`step()` 안에서 부르지 않는다.** `AI.think(state, slot) → {dx, dy, buttons}` 로 입력만 만들고, 그 입력을 사람 입력과 똑같은 통로로 넣는다.
  그래서 서버 권위·결정성·리플레이가 전부 그대로다(같은 상태 → 같은 입력, 난수 없음).
- 판단은 네 가지뿐이다: ① 내가 공을 가짐 → 골대로 몰고 가다 300 안이면 9틱 충전 후 슛, 붙으면 패스 ②
  팀원이 가짐 → 앞쪽으로 벌려 받을 자리 ③ 상대가 가짐 → 가까운 한 명이 앞을 잘라 쫓고 발차기, 다른 한 명은
  우리 진영이면 슛 길목, 아니면 남은 상대를 맡음 ④ 주인 없음 → 가까우면 공, 아니면 중간 지점.
- 체력이 남을 때만 달린다(임계값은 상황마다 다르다).
- **`AI.reset()`** 을 경기 시작 때 부른다(충전 상태 초기화).

## 6. 프로토콜

텍스트 프레임은 JSON `{ t: '종류', ... }`, 바이너리 프레임은 첫 바이트가 종류다.

**C→S (텍스트)**: `hello {v, nick, token?}` · `pong {id}` · `room.list` · `room.create {name, teamSize, halfSec, pass?, classA?, classB?}`(pass 가 있으면 비밀번호 방) · `room.join {id, pass?}` · `room.leave` ·
`team {team}` · `char {id}` · `ready {on}` · `start` · `chat {text}`
**C→S (바이너리, 6B)**: `[0x01, seq u16 LE, buttons u8, dx i8, dy i8]` — buttons 비트: 0 패스(Z) 1 슛·발차기(D) 2 드리블(W) 3 감아차기왼쪽(Q) 4 감아차기오른쪽(E) **5 방귀(S)** 6 필살기(A) 7 달리기(왼쪽 Shift). dx,dy는 −127~127 → −1~1 (방향만 쓴다).
**S→C (텍스트)**: `ping {id}` · `welcome {slotToken, rtt, p90, serverTime}` · `reject {code, msg, rtt?, p90?, limit?}`(이후 close) ·
`rooms {list}`(각 항목 `{id, name, teamSize, halfSec, lock, players, cap, phase, classes, host}`) ·
`room {state}`(방 전체: `{id, name, teamSize, halfSec, lock, classes, hostId, phase, cap, members:[{id, nick, team, char, ready, slot, host, rtt}]}`) ·
`joined {id}` · `left` · `error {msg}`(비밀번호 틀림·자리 없음 등 **끊지 않는 실패**) · `match.start` · `match.end {why}` ·
`event {kind, ...}` · `chat {from, text}` · `kick {code, msg}`(이후 close)
클라이언트가 받는 경기 이벤트 종류: `kickoff` `play` `goal` `half` `end` `lobby` `kick` `fart` `shoot` `curve` `pass` `dribble` `hit` `steal` `keeperSave` `ult`
**S→C (바이너리, 스냅샷)**: `[0x02, tick u32, serverMs u32, phase u8, scoreA u8, scoreB u8, clock u16, ballX i16, ballY i16, ballVx i16, ballVy i16, owner u8,
keeperY0 i16, keeperY1 i16, keeperFlags u8, n u8, n × (slot u8, x i16, y i16, vx i16, vy i16, facing u8, state u8, ult u8, motion u8)]` — 헤더 29B + 선수당 13B.
좌표·속도는 ×4 고정소수, facing 0~255 = 0~2π. `ult` 바이트는 **하위 4비트 필살기 게이지 + 상위 4비트 달리기 체력**(각 0~15)이다 —
선수 레코드를 13B 로 유지하려는 절충이라 게이지 눈금이 1/15 로 거칠다(만충 여부는 state 비트 6 이 정확히 알려 준다).
`motion` = 하위 4비트 동작(0 idle 1 run 2 kick **3 fart** 4 stun 5 ult) + 상위 4비트 충전 0~15.
keeperFlags 비트0/1 = 골키퍼 0/1 이 방금 공을 튕겨냄(이펙트용). phase 바이트: 하위 7비트 단계(0 lobby 1 kickoff 2 play 3 goal 4 half 5 end), 비트7 = 후반.
state 비트: 0 공 소유 1 발차기 중 2 기절 3 충전 중 4 필살기 발동 중 **5 방귀** 6 필살기 만충 7 팀.
20명 기준 **289바이트**, 20Hz → 1인당 5.8KB/s, 한 방 약 0.9Mbps.

**접속 절차**: open → 서버 `ping`×8(100ms 간격) → 클라이언트 즉시 `pong` → 서버가 RTT 중앙값·p90 계산 → 통과면 `welcome`, 아니면 `reject{code:'NET_SLOW'}` + close 4001.
`hello`는 첫 `ping` 전에 보낸다(버전 검사가 먼저: 불일치면 4002). 통과 후에만 `room.*`을 받는다.
**시계 동기**: 설계는 `offset = serverMs + rtt/2 − localMs` 였으나, **구현은 스냅샷이 도착한 로컬 시각을 그대로 보간 기준으로 쓴다**(연습장과 같은 경로).
서버 시계를 맞추지 않아도 버퍼가 도착 순서대로 쌓이므로 보간이 부드럽고, 코드가 한 갈래로 줄어든다. 예측이 필요해지는 선택 10단계에서 다시 볼 것.

**방장·준비·시작**: 방을 만든 사람이 방장이고, 나가면 다음 사람에게 넘어간다. 시작 조건은 세 가지를 모두 만족해야 한다 —
① 인원이 정원과 같다(`members.length === teamSize × 2`) ② 양 팀 인원이 같다 ③ 전원 `ready`. 하나라도 어긋나면 `error` 로 이유를 돌려준다.
**비밀번호 방**: `pass` 는 서버에만 있고 목록에는 `lock: true` 로만 나간다. 틀리면 `error` 로 알리고 **소켓은 끊지 않는다**.

### 7.1 시야와 카메라 (클라이언트 전용)

**추종 방식**(2026-08-25 7차 지시): **내 선수가 항상 화면 한가운데** 온다. 데드존(`CAM.deadX/deadY`)을 0 으로 두어 카메라 목표가 곧 내 좌표다.
다만 **경기장 가장자리에서는 가운데가 아니어도 된다** — 골망 밖을 보여 주지 않으려는 클램프가 카메라를 붙잡기 때문에 자연히 그렇게 된다.
실측(시야 640×360): 한가운데(600,400)와 오른쪽 위(900,250)에서는 카메라와 선수의 차이가 **0,0**,
왼쪽 끝(40,400)에서는 x 차이 **240**, 위쪽 끝(600,40)에서는 y 차이 **140**.

경기장 전체를 보여주지 않는다(2026-08-24 사용자 지시). 카메라가 내 선수를 따라간다.

- **보이는 넓이(면적)를 고정한다.** 세로만 고정하면 화면비가 극단일 때 무너진다 — 세로 폰(375×812)에서 가로 138단위(선수 5명 폭)만 보이고,
  32:9 초광각에서는 경기장의 75%가 보여 불공평했다. 그래서 넓이 기준으로 바꿨다:

  ```
  scale = sqrt(캔버스폭 × 캔버스높이 / VIEW_AREA)      // 넓이 고정
  sMax  = min(캔버스폭 / VIEW_W_MIN, 캔버스높이 / VIEW_H_MIN)   // 이보다 크면 너무 조금 보인다
  sMin  = 캔버스폭 / VIEW_W_MAX                                  // 이보다 작으면 너무 많이 보인다(공평성)
  scale = sMin > sMax ? sMin : clamp(scale, sMin, sMax)          // 충돌하면 공평성 우선
  ```

  `VIEW_AREA_PC` 230400 · `VIEW_AREA_TOUCH` 195000 · `VIEW_W_MAX` 880 · `VIEW_W_MIN` 300 · `VIEW_H_MIN` 288(골대 폭 200 + 여유 44씩).
  폰이 PC보다 15% 덜 보는 이유: 화면이 작아 같은 넓이를 보여 주면 선수가 각(角)으로 3.6배 작아진다. 공평성 손해는 없다(폰이 **덜** 본다).
  캔버스 크기는 device px 라서 분자·분모가 같이 dpr 배가 된다 → 보이는 월드 넓이는 **dpr 과 무관**하다(레티나에서 더 보이지 않는다).
  실측: 1920×1080·1366×768 → 640×360 / 21:9 → 742×311 / 32:9 → 880×248 / 4:3 → 554×416 / 폰 가로 → 650×300 / 폰 세로 → 300×650.
- 데드존 ±46×34 월드 단위를 벗어나야 카메라가 움직이고, `1 - exp(-dt/0.10)` 로 부드럽게 따라간다(프레임률 무관).
- 골망(깊이 40)까지 포함해 경기장 밖이 보이지 않게 클램프한다.
- 좁은 시야를 보완하는 장치 — 없으면 공을 찾을 수 없다: **미니맵**(우상단, 양 팀 점·공·골대·카메라 사각형, M 키로 토글),
  **화면 밖 공 화살표**(가장자리에 방향 + 거리).
- 화면 밖 선수는 그리지 않는다(`onScreen`, 여유 80). `stats().drawn` 으로 확인.

## 8. 실행·검증 환경

**온라인 서버 실행**:
```
cd soccer/server && npm install && npm start     # → http://localhost:8080/
```
서버가 `soccer/` 전체를 정적으로 서빙하므로 브라우저는 서버 주소 하나만 열면 된다(`index.html`·`game-core.js`·`sprites.js` 모두 `no-cache`).

`node loadtest.js --players 4` 로 방 생성 → 입장 → 준비 → 시작 → 경기까지 사람 없이 재현한다(`--delay`·`--drop`·`--delayAfter` 로 게이트·퇴장 검증).

- 로컬: `cd soccer/server && npm install && npm start` → `http://localhost:8080/`. 연습장만이면 루트 정적 서버 `http://localhost:8765/soccer/` 또는 `file://`.

## 9. 배포 — **내 PC + Cloudflare 빠른 터널** (2026-08-25 사용자 결정, 무료)

서버를 사용자 PC 에서 돌리고 Cloudflare 빠른 터널로 바깥에 낸다. 유료 호스팅(Lightsail)은 **쓰지 않기로 했다**.

```
powershell -ExecutionPolicy Bypass -File soccer/server/start-online.ps1
```
서버(8080) + 터널을 함께 띄우고 `https://<무작위>.trycloudflare.com` 주소를 찍어 준다. 그 주소를 친구에게 주면 끝이다.

**빠른 터널을 고른 이유** — 사용자가 예전에 Cloudflare 로 막혔던 것은 **이름 있는 터널**(`cloudflared tunnel login` → `route dns`)이었다.
그쪽은 Cloudflare 계정과 **본인 소유 도메인**이 있어야 하고 브라우저 로그인이 필요해서 자동화가 안 된다.
`tunnel --url` 은 **계정·도메인·로그인이 전혀 없다.** 실측(2026-08-25):

| 방식 | 접속 지연(서버가 잰 왕복) | 판정 |
|---|---|---|
| localhost.run (ssh, 무설치) | **411ms** | 게이트에서 거부 — 실시간 게임 불가 |
| **Cloudflare 빠른 터널** | **중앙값 14ms · 상위10% 26ms** | 통과. 서울 노드(`icn06`)에 붙는다 |

같은 도구로 터널 주소에 대고 전 과정을 재현할 수 있다:
`node loadtest.js --url https://<주소> --players 4` → 입장·비밀번호·준비·시작·스냅샷 20.2Hz 확인(2026-08-25 실측).

### 9.1 주소 게시판 — 바뀌는 주소를 자동으로 따라가기

빠른 터널의 유일한 약점은 "주소가 매번 바뀐다"이다. 대문(GitHub Pages)에 올린 정적 사본은 그 주소를 알 수 없다.
그래서 **주소를 적어 두는 고정된 자리**를 하나 둔다 — `server/url-registry.js`(Deno Deploy, 무료, 40줄).

```
[내 PC] start-online.ps1 ─ 터널 열고 새 주소를 게시판에 POST
[게시판] https://gray-macaque-4849.woo-design22.deno.net   ← 주소 하나만 들고 있는다
[대문]  게임 페이지가 GET 으로 읽어 서버 주소 칸을 자동으로 채운다
```

- 쓰기는 `WRITE_KEY` 를 아는 쪽만(내 PC). 읽기는 누구나 — 나오는 것은 그 순간 터널 주소뿐이고, 실제 차단은 방 비밀번호다.
- **저장소는 Deno KV 이되, 앱에 KV 가 붙어 있지 않으면 메모리로 자동 전환**한다.
  `Deno.openKv()` 를 그냥 부르면 KV 미연결 시 **앱 자체가 안 뜬다**(2026-08-25 실제로 겪음: `no KV database is attached`).
  지금 어느 쪽으로 도는지는 `GET /` 응답의 `store` 값(`kv` / `memory`)으로 확인한다.
  메모리 모드는 앱이 잠들거나 인스턴스가 바뀌면 주소를 잊으므로(터널을 다시 켜면 복구), 대시보드에서 KV 를 연결해 두는 편이 낫다.
- **30분 넘게 갱신이 없으면 `stale: true`** 로 표시해 꺼진 서버 주소로 붙는 것을 막는다.
  스크립트가 정상 종료하면 게시판을 비우기까지 한다.
- 클라이언트의 주소 우선순위: ①주소창 `?server=` ②직접 입력(저장됨) ③**게시판** ④이 페이지를 준 서버.
  `index.html` 의 `REGISTRY` 상수가 비어 있으면 이 기능은 꺼진 것과 같다(서버가 페이지도 서빙하는 평소 경로에는 필요 없다).
- 비밀은 `server/registry.txt`(1줄 주소 / 2줄 키)에 두고 **커밋하지 않는다**(`server/.gitignore`). 키는 코드에 절대 넣지 않는다 —
  Playground 코드는 공개될 수 있지만 환경변수는 아니다.
- **Deno Deploy Classic 은 2026-07-20 에 종료됐다.** 새 콘솔은 `console.deno.com` 이고 앱 주소는
  `https://<앱이름>.<조직이름>.deno.net` 형식이다(옛 `*.deno.dev` 는 404 `DEPLOYMENT_NOT_FOUND`).
  이 저장소의 게시판 주소는 `https://gray-macaque-4849.woo-design22.deno.net` 이고 `index.html` 의 `REGISTRY` 상수에 박혀 있다.

**한계**
- **주소가 매번 바뀐다.** 터널을 다시 켜면 새 주소다. 고정 주소는 Cloudflare 계정 + 도메인이 있어야 한다.
- **PC 를 켜 두어야 한다.** 창을 닫으면 접속이 끊긴다.
- 대문(GitHub Pages)에 올린 사본은 정적이라 서버가 없다. 그 사본에서 온라인을 하려면 로비 화면의
  **서버 주소 칸**에 그날의 터널 주소를 넣거나, 주소창에 `?server=https://<주소>` 를 붙인다(입력값은 `soc_server` 에 저장된다).
- 터널을 켜는 동안은 **누구나 그 주소로 들어올 수 있다.** 방 비밀번호로 막는다.
